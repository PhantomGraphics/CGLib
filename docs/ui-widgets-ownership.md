# UIWidgets の所有権・寿命の規約

`docs/todo/PLAN_cglib_refactoring.md` Phase 5。`UIWidgets/IWindow.h`・`IView.h`・`Panel.h` の実装から読み取った
現行の契約を文書化したもの（挙動の変更は伴わない）。

## 規約

1. **子は非所有。** `IWindow::add(IWindow* child)` は生ポインタを `std::list<IWindow*> children` に積むだけで、
   所有権は移らない。`shared_ptr` 化はしない（全ポインタを一律に共有所有へ変えると、描画ツリーの寿命が
   データモデルの寿命と絡み合うため。必要な箇所だけ呼び出し側が所有する）。
2. **子は親より長く生きること。** 親の `show()`/`onShow()` は毎フレーム全ての子を辿る。親が生きている間に子を
   破棄すると、次のフレームで解放済みオブジェクトを呼ぶ。典型的な安全な構成は次の 2 つ:
   - 子と親を同じクラスのメンバー（または同じスコープの自動変数）にする。メンバーは宣言の**逆順**で破棄されるので、
     親を子より**後に**宣言すれば親が先に破棄され、破棄済みの子を親が辿ることはない（子を親より後に宣言すると、
     親のデストラクタ中は問題なくても、その間に `show()` が呼ばれる設計では危険）。
   - 子を `unique_ptr` 等で所有する側が親も所有し、親の破棄・`clear()` を先に行う。
3. **コピー禁止。** `IWindow` は `UnCopyable` を private 継承する。ムーブも未定義なので、ウィジェットは値で持ち回さず、
   メンバーとして直接置く（`CGLib/CLAUDE.md` の VKG クラスの規約と同じ）。
4. **削除手段は `clear()` のみ。** 子を 1 つだけ外す `remove(child)` は現状ない（利用箇所が無い。`Panel::clear` 相当の
   全消去だけで足りている）。個別に外す必要が出たら `children.remove(child)` を足す（`list` なので他の子の
   反復は壊れない）。反復中の `add`/`clear`（`onShow()` 内からの変更）は未定義とみなし、1 フレームの
   構築はフレーム外（`onUpdate()` 等）で行う。
5. **表示条件は構築時に 1 回登録。** `setVisibleWhen(fn)` の述語は毎フレーム評価される。述語が捕捉する参照・
   ポインタは、そのウィジェットより長く生きること（規約 2 と同じ理由）。述語は状態を変更しない。
6. **スレッド。** 全て ImGui のフレーム（描画スレッド）上で完結する。別スレッドから `add`/`clear`/`show` を
   呼ばない。他スレッドの要求は `CommandQueue`（`VkAppBase/ScenarioRunner/CommandQueue.h`）経由で描画スレッドに渡す。

## 確認済みの利用実態（2026-10-06）

- `children.erase/clear/remove` の呼び出しは `IWindow::clear()` と `Panel::clear` 相当のみ（他の UI コードからの
  個別削除なし）。
- 宣言的 UI（`Row`/`Section`/`Window`/`Menu`/`bind()`）の個別の寿命パターンは、この調査では 1 件ずつ検証していない。
  新規コードは上の規約 2 の 2 構成のどちらかに揃える。

## 将来検討（必要になった場合のみ）

- `IWindow::remove(IWindow*)`（動的に出し入れするパネル用）。
- デバッグビルド限定の検査（`show()` 中の `add`/`clear` を `assert` で検出）。
